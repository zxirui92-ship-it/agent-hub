# 项目作业：企业级「智能运营中枢」Agent 平台（七大架构综合实战）

---

## 一、业务背景（企业真实痛点）

**公司**：星潮电商（日均订单 12 万单，客服团队 40 人，运营团队 15 人）

**业务痛点**：

| 痛点 | 现状 | 业务目标 |
|------|------|----------|
| 客服 60% 问题为重复性 FAQ，人力成本高 | 人工日均处理 3000 会话 | 智能客服承接 70% 简单会话 |
| 客服查订单/物流/库存需切换 5 个系统 | 单次查询平均 90 秒 | 一次对话内实时查数，降至 10 秒 |
| 运营周报靠人工汇总 6 个数据源 | 每周耗时 8 人时 | 自动生成结构化周报 |
| 内部工具能力散落（搜索/代码/知识库/生图） | 无统一入口，各系统独立 | 统一网关按需分发能力 |
| 大促方案需产品/运营/数据/客服 4 方反复拉会 | 单方案评审周期 5 天 | AI 多角色协同，周期压至 1 天 |
| 订单、行为、营销数据模块各自为政 | 数据口径不一致，对账难 | 共享状态池，口径统一 |
| 退款/合规审批流程口头化，无回滚无审计 | 差错率 3%，无法追责 | 流程固化、可监控、可回滚 |

**项目目标**：交付一个覆盖 **7 类 Agent 架构** 的智能运营中枢，作为公司 AI 中台 V1.0。

---

## 二、核心知识点覆盖映射表（每个知识点必须落地）

| # | 核心知识点 | 落地模块 | 需求/代码中的体现（验收点） |
|---|-----------|---------|---------------------------|
| 1 | **单 Agent 架构** | M1 FAQ 闲聊客服 | 单 LLM + 记忆 + 2 个简单工具，`single_agent.py` 可独立运行 |
| 2 | **ReAct 架构** | M2 订单/物流实时查询 | 代码中可见 Thought→Action→Observation 循环轨迹与终止条件，`react_agent.py` 打印完整推理链 |
| 3 | **Plan&Execute 架构** | M3 运营周报生成 | Planner 拆解为分步计划，Executor 逐步执行，结果汇总；计划与执行分离的类/函数边界清晰 |
| 4 | **Router+Skill 架构** | M4 统一能力网关 | Router 对输入分类分发；≥4 个 Skill 插件（搜索/知识库/代码/生图），新增 Skill 无需改 Router 主逻辑（可插拔） |
| 5 | **Multi-Agent 架构** | M5 大促方案协同 | Orchestrator + 产品/运营/数据/客服 4 个专业 Agent，有明确的任务分配与结果汇总 |
| 6 | **Blackboard 架构** | M6 多源数据融合 | 存在全局共享状态空间（黑板对象/表），各 Agent 读→处理→写回，其他 Agent 响应更新 |
| 7 | **Graph/Workflow 架构** | M7 退款合规流程 | 基于 LangGraph 构建 DAG：条件分支节点、聚合校验节点、反思回跳边、全局 State，可回滚 |
| 8 | **选型决策树** | 全局 | 需求文档中必须用「快速决策树」对 7 个模块逐一给出选型论证（含否决其他架构的理由） |

## 三、功能需求

### M1 单 Agent 智能客服（简单会话）
- 支持多轮闲聊与 FAQ 问答，带会话记忆（窗口可配置）
- 输出：直接回答

### M2 ReAct 实时业务查询
- 输入"查订单 2025101234 的物流到哪了"，循环调用 `query_order`、`query_logistics` 工具
- 必须输出完整推理轨迹（思考/行动/观察三段日志）
- 含"是否达标"判断，未达标继续循环，最多 N 轮防死循环

### M3 Plan&Execute 周报生成
- 输入目标"生成第 X 周运营周报"
- Planner 输出编号计划（拉取销售数据→环比分析→异常归因→生成报告）
- Executor 逐步执行，最终汇总为 Markdown 周报

### M4 Router+Skill 能力网关
- 输入路由到：联网搜索 / 企业知识库问答 / 代码生成 / 图片生成 ≥4 个 Skill
- Skill 统一接口规范（如 `class Skill: def run(self, input) -> str`），注册式加载
- 路由错误时有兜底策略

### M5 Multi-Agent 大促方案协同
- Orchestrator 拆解目标 → 分派给产品、运营、数据、客服 4 个 Agent（可并行/串行）
- Agent 间有通信机制（消息传递），最后统一汇总为一份完整方案

### M6 Blackboard 数据融合
- 定义全局黑板（订单数据、用户行为、营销活动三类共享状态）
- 至少 2 个 Agent 往黑板写入、至少 1 个 Agent 依赖他人写入结果后继续处理
- 日志体现"读黑板→处理→写回→触发响应"

### M7 Graph/Workflow 退款合规流程
- LangGraph 定义：Start → 受理节点 → 金额条件分支（≤500 自动过 / >500 人工审核节点）→ 合规校验节点 → 反思循环（不通过回跳）→ 结束
- 全局 State 贯穿，支持状态回滚与执行轨迹查询

### 非功能需求
- 模块间低耦合，M1–M7 可独立启动演示
- 关键链路有日志、异常有兜底处理

## 四、代码规范（企业工程标准）

1. **技术栈**：Python 3.10+ / LangChain / LangGraph（M7 必须）/ 任一 LLM API；依赖写入 `requirements.txt`
2. **目录结构**：

```
agent-hub/
├── README.md              # 项目说明+运行方式
├── requirements.txt
├── docs/                  # 需求文档、选型论证、架构图
├── agents/
│   ├── single_agent.py    # M1
│   ├── react_agent.py     # M2
│   ├── plan_execute.py    # M3
│   ├── router/            # M4 路由与 skills/
│   ├── multi_agent.py     # M5
│   ├── blackboard.py      # M6
│   └── workflow/          # M7 LangGraph
├── common/                # 工具、LLM 封装、日志
└── tests/                 # 每模块至少 1 个用例
```

3. **命名**：模块/函数蛇形命名，类驼峰命名；常量大写
4. **注释**：每个架构模块头部注明架构名、核心思想、流程（与课件口径一致）
5. **Git**：≥5 次有意义 commit，禁止一次性提交
6. **安全**：API Key 走环境变量，严禁硬编码入库
